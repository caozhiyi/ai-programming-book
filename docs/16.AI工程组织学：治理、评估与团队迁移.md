# 16. AI 工程组织学：治理、评估与团队迁移

三个月前，你的团队引入了 AI 编程助手。前两周所有人都很兴奋——代码生成速度明显提升，重复性的样板代码不用手写了，写测试也不再那么痛苦。有人在团队群里发了一张截图：AI 帮他在十分钟内完成了一个原本需要两小时的 CRUD 模块。

第三周开始出问题了。张三让 AI 生成的代码用了 `log.Printf`，李四的用了 `slog`，王五的用了 `zap`——三个人做的是同一个项目，没人知道团队的日志规范到底是什么。有人写了一个 Skill 定义了编码规范，但这个 Skill 存在他自己的电脑上，其他人不知道有这个东西，两周后他改了内容也没通知任何人。模型提供商发布了新版本，有人直接切换了，然后一堆原本跑得好好的任务开始出奇怪的结果——Prompt 的措辞在新模型上的效果不一样了，但没人做过回归测试，大家以为是自己的代码有 bug，排查了两天。记忆库越来越大，三个月积累了几百条记忆，其中有些已经过时——"数据库用 MySQL"，但项目两周前已经迁移到了 PostgreSQL，没人清理过记忆库，因为没人觉得这是自己的职责。

这些问题有一个共同特征：它们都不是技术问题。系统的每个技术组件都在正常工作——模型在推理、工具在执行、Skill 在加载、记忆在检索。但整个系统的输出质量在下降，因为没有人在"运营"这套系统。技术问题最终都会变成组织问题——这不是 AI 系统的独特现象，微服务架构也是这样：技术上可以拆得很细，但如果没有对应的组织能力来支撑，拆了反而更乱。

那么这套系统在真实团队里，由谁来建？谁来维护？谁来演进？

## 16.1 静默腐烂：AI 系统的技术债长什么样

传统软件的技术债你很熟悉——过时的依赖、缺失的测试、混乱的代码结构、没人看得懂的历史逻辑。AI 系统引入了一类新的技术债，它们不是代码，但和代码一样会腐烂。而且腐烂的方式更危险：**它是静默的。**

代码腐烂了，编译器会报错、测试会失败、用户会投诉。但 Prompt 腐烂了系统不会报错——它只是输出质量悄悄下降。你写了一个 System Prompt，效果很好。三个月后，项目的技术栈变了、业务逻辑变了、模型也升级了——但 Prompt 还是三个月前的那个。它不会编译失败，不会有测试告诉你"这个 Prompt 过时了"，它只是默默地产出越来越不合适的结果。

Prompt 的腐烂会传染。团队里有人写了五个 Skill，分别覆盖编码规范、测试策略、API 设计、错误处理、文档风格。半年后，其中两个已经和项目现状不符，一个有内容冲突（编码规范 Skill 说"错误用 `fmt.Errorf`"，错误处理 Skill 说"错误用 `errors.New`"），还有一个从来没人用过但也没人敢删。Skill 冲突了系统不会崩溃——它只是行为变得不可预测。

记忆库的腐烂更隐蔽。记忆是只增不减的——每次对话都可能产生新的记忆条目。三个月后，记忆库里有"用 MySQL"也有"用 PostgreSQL"，有"测试覆盖率要求 80%"也有"测试覆盖率要求 60%"。哪个是最新的？没有时间戳能告诉你，因为旧的记忆没有被标记为"已废弃"，它只是和新的记忆共存，偶尔给出奇怪的建议。

而你用来检测这些问题的工具——评估集——本身也在腐烂。你在上线时构建了 50 个测试用例，系统运行半年遇到了 20 种新的失败模式，但评估集还是那 50 个用例，通过率一直是 90%。你以为系统质量稳定，实际上系统在新的失败模式上表现很差——只是你的评估集没有覆盖到。知识库也是同理：项目文档更新了，但知识库的索引没有重建，AI 基于过时的文档给出建议——它不知道文档已经变了。

静默的腐烂比显性的故障更危险，因为你不知道它在发生，直到后果已经积累到无法忽视的程度。这就是为什么这些资产需要和代码一样被治理——有版本管理、有审查流程、有更新机制、有退役策略。

## 16.2 谁来治理：职责必须有人承担

治理需要人来做。问题是：谁来做？

不是"要不要招新人"的问题——而是"这些职责有没有人明确承担"的问题。在小团队里，一个人可能兼任多个角色，但职责本身必须被识别出来，否则就会变成"大家都觉得是别人的事"。

从使用端开始想。团队里每天用 AI 编程工具写代码的人——应用工程师——是系统的主要用户，也是问题的第一发现者。"AI 今天生成的代码风格变了"、"这个 Skill 好像不生效了"、"记忆里有一条过时的信息"——这些信号最先被他们感知到。他们不需要理解系统的内部机制，但需要知道怎么有效地使用系统、怎么反馈问题。

但谁来处理这些反馈？这就引出了第二层职责：规范维护。有人需要负责编写和维护 Prompt、Spec、Skill。这个角色最容易被忽视，因为"写一个 Skill"看起来是一次性的工作，但实际上它需要持续迭代——项目的编码规范变了 Skill 要跟着变，模型升级了 Prompt 的措辞可能需要调整，新的业务场景出现了可能需要新的 Skill，旧的 Skill 不再适用了需要被明确废弃。在大多数团队里由资深工程师兼任，但关键是这个职责要被明确分配，而不是"谁有空谁来做"。

规范写好了，怎么知道它有没有效？这引出了第三层职责：评估。有人需要构建评估集、定义质量标准、监控线上指标。这个角色在传统团队里最接近 QA，但有一个根本性的不同：传统 QA 测试的是确定性系统——同样的输入必须产生同样的输出；AI 系统是非确定性的——同样的输入可能产生不同的输出。评估负责人需要理解这种非确定性，设计出能在非确定性中衡量质量的评估方法。

如果团队开始自建 MCP Server、自建 RAG 管道、自建评估系统，还需要第四层职责：基础设施运维。MCP Server 的部署和维护、RAG 管道的运营、记忆库的治理、模型接入层的管理——不是每个团队都需要这个角色，如果你只用一个现成的 AI 编程助手就不需要，但一旦开始自建就需要有人来运维。当 AI 系统能访问生产数据或执行部署操作时，安全与治理的职责也必须被明确承担——定义权限边界、审批高风险操作、制定数据安全策略。

这里有一个关键的认知：这些职责不应该集中到一个独立的"AI 团队"。应用工程师是所有开发者，规范维护者是资深工程师，评估负责人可能是 QA，基础设施运维可能是 DevOps。如果把所有 AI 相关的事都集中到一个"AI 团队"，会出现一个问题：AI 团队不理解业务需求，业务团队不理解 AI 能力，规范写得不贴合实际，评估标准脱离业务场景。AI 编程系统的运营应该是嵌入式的——嵌入到现有的工程团队中，而不是独立成一个新团队。

## 16.3 像管理代码一样管理 AI 资产

角色明确了，接下来是机制。核心原则只有一条：**每一类资产都需要明确的 Owner、明确的更新触发条件、明确的审查流程。** 这条原则不新鲜——它就是你管理代码的方式。代码有 Owner、有 PR 审查、有 CI 验证、有发布流程。AI 资产需要同样的待遇。

Prompt 和 Spec 应该像代码一样纳入版本控制——放在项目仓库里，和代码一起提交、一起审查、一起发布。每次修改都应该有 commit message，说明为什么改、改了什么、预期效果是什么。"优化了 Prompt"不是一个好的 commit message——"调整错误处理的 Prompt 措辞，因为模型升级后旧措辞导致错误处理代码缺少 wrap context"才是。修改 Prompt 和修改代码一样需要审查，但审查的重点不同：不是"语法对不对"，而是"这个修改会怎么影响 AI 的行为"。这比代码审查更难，因为 Prompt 的修改和行为变化之间的关系不是确定性的——一个看起来很小的措辞调整，可能导致 AI 在某些场景下的行为发生显著变化。所以 Prompt 的修改应该配合评估——改完之后在评估集上跑一遍，确认质量没有退化。

Skill 需要完整的生命周期管理：创建 → 测试 → 发布 → 迭代 → 废弃。创建时明确要解决什么问题、适用于什么场景。测试时在典型场景上验证效果——加载了这个 Skill 之后，AI 的行为是否符合预期？发布时让团队知道有这个 Skill、怎么使用。迭代时走版本管理和审查流程。废弃时明确标记并从默认加载列表中移除——不要让过时的 Skill 继续存在，它不会报错，但会悄悄地误导 AI。

记忆库需要定期清理：过时的记忆、冲突的记忆、重复的记忆。多久清理一次取决于记忆的增长速度——如果团队每天产生大量新记忆可能需要每周清理，如果增长缓慢每月一次可能就够了。一个更好的方式是给记忆加上"有效期"或"置信度"——时间越久置信度越低，当新记忆和旧记忆冲突时优先采用新记忆。但这需要记忆系统本身支持这种机制。

评估集需要持续扩充，这需要一个闭环：线上发现问题 → 分析根因 → 构建评估用例 → 加入评估集 → 下次回归时自动验证。如果没有这个闭环，评估集会越来越"过时"——通过率 90% 不代表系统质量好，可能只是评估集太旧了。知识库的同步则相对简单：最好的方式是在 CI/CD 管道中加一步——每次文档更新时自动触发知识库的重新索引。

评估不只是技术方法，它是一个需要持续运营的组织流程。评估标准反映的是"组织对 AI 输出质量的期望"——这个期望需要多方参与：业务方关心"AI 生成的代码是否满足业务需求"，安全团队关心"是否有安全漏洞"，QA 关心"是否可测试"，工程团队关心"是否符合编码规范"。评估标准应该是这些关注点的综合。

运营节奏也需要明确。离线评估不是"想起来就跑一次"——模型升级时必须跑，Prompt 或 Skill 修改时必须跑，即使没有任何变更也应该每两周跑一次（因为外部环境可能变了）。线上指标需要持续监控：任务成功率、用户接受率、二次修改率。这些指标的趋势比绝对值更重要——任务成功率从 85% 下降到 75%，即使 75% 看起来还不错，下降趋势本身就是一个信号。定期复盘评估数据，目标不是"看看数字"，而是"识别系统的薄弱环节，驱动改进"——复盘的输出应该是具体的改进行动。

## 16.4 模型升级：AI 系统独有的变更管理

传统软件升级一个依赖库，你可以通过单元测试确认兼容性，测试通过了大概率没问题。模型升级不是这样的。

模型升级改变的不是"接口"——接口可能完全没变，输入格式一样、输出格式一样、API 调用方式一样。改变的是"行为模式"——同样的 Prompt，新模型可能理解得不一样、推理得不一样、生成得不一样。一个具体的例子：你的 Prompt 里有一条规则"如果用户没有指定错误处理方式，默认使用 wrap error 模式"，旧模型对这条规则的遵循率是 95%，新模型可能是 98%——更好了，但也可能是 80%——因为新模型对"默认"这个词的理解发生了微妙的变化。你不会收到通知说"新模型对'默认'这个词的理解变了"，你只会看到——如果你有评估体系的话——评估集上某些用例的通过率下降了。如果你没有评估体系，你什么都看不到，直到用户开始抱怨。

所以模型升级应该被当作"基础设施变更"来管理，流程是：评估 → 灰度 → 观察 → 全量。评估阶段在评估集上跑新模型，和旧模型的结果做对比，关注的不只是"通过率"——还有"输出风格是否变化"、"Token 消耗是否变化"、"延迟是否变化"。灰度阶段不要一次性切换所有用户，先让一小部分用户或一小部分任务类型使用新模型观察效果。观察阶段持续监控线上指标，如果指标下降立即回滚。灰度期间指标稳定，再全量切换。

谁有权决定切换模型？这不是某个工程师能单独决定的——需要评估负责人确认质量没有退化，规范维护者确认现有的 Prompt 和 Skill 在新模型上是否需要调整，平台角色确认新模型的 API 兼容性、性能特征、成本变化。

回滚机制是升级计划的必要组成部分。如果新模型上线后质量下降，需要能快速回滚到旧模型——不是"改配置文件然后重启"，而是"一键切换，立即生效"。回滚不只是切换模型：如果你为新模型调整了 Prompt 或 Skill，回滚时也需要把 Prompt 和 Skill 一起回滚。这就是为什么 Prompt 和 Skill 需要版本管理——你需要能回到"旧模型 + 旧 Prompt + 旧 Skill"的完整状态。模型升级后现有的 Prompt 和 Skill 可能需要调整，这个适配工作量需要在升级之前就评估——如果适配成本太高，可能需要推迟升级，或者分阶段升级：先升级对 Prompt 变化不敏感的场景，再逐步升级敏感场景。

## 16.5 成熟度自评：你的团队在哪里

前面几节讲了"应该怎么做"。但不是每个团队都需要一步到位。关键是知道自己在哪里，以及下一步该做什么。

![团队迁移路径：从 L0 到 L4 的关键动作与风险](images/16-team-migration-path.svg)

问自己几个问题，就能定位你的团队：

**团队成员使用 AI 的方式一致吗？** 如果每个人都在用自己的方式和 AI 对话，手工复制粘贴上下文，没有规范、没有评估、没有记忆——你在 L0（对话式使用）。AI 的输出质量完全取决于个人的 Prompt 能力。下一步是接入一个能调用工具的 Agent 环境，这通常是最容易跨越的一步。

**AI 的输出风格在团队内一致吗？** 如果 Agent 已经跑起来了——能读代码、查文件、跑命令——但输出风格不一致、每次新会话都要重新解释项目背景、不知道 AI 的输出质量怎么样——你在 L1（单 Agent + 基础工具）。下一步是建规范：把团队的编码规范、架构约定写成 Skill 或 Spec，接入项目知识库，启用记忆系统。这需要投入时间但不需要复杂的基础设施。到了 L2（有规范、有知识注入），AI 的输出风格趋于一致，输出质量开始稳定。

**你能量化 AI 的输出质量吗？** 如果不能——你还在 L2 以下。下一步是建评估：构建评估集、定义质量标准、搭建监控。这是一个显著的投入，不只是技术投入还有认知投入——"什么是好的 AI 输出"这个问题本身就不容易回答。到了 L3（有评估、有可观测性），你能衡量 AI 的输出质量，出了问题能追溯——知道 AI 看到了什么上下文、做了什么决策、调用了什么工具。

**模型升级时你有回归测试吗？Prompt 和 Skill 有版本管理和审查流程吗？** 如果没有——你还在 L4 以下。L4（团队级 AI 工程系统）意味着完整的治理流程——资产有 Owner、有版本管理、有审查机制；有模型升级的变更管理——评估、灰度、回滚；有安全边界——权限最小化、分级授权；有持续演进的机制——评估驱动改进、复盘驱动迭代。

大多数团队从 L0 到 L2 就能获得显著的收益。L3 和 L4 是当你开始依赖 AI 输出质量、需要系统化治理时才需要的。不需要一步到位——但需要知道自己在哪里，以及下一步该做什么。

**3-5 人小团队的最小可行治理。** 上面的成熟度模型可能让小团队觉得"这些都是大公司才需要的"。不是的。3-5 人的团队用最低成本就能达到 L2 级别，只需要三样东西：

第一，**一个共享的规范文件**。在项目仓库根目录放一个 `.cursorrules`（或你的工具对应的规范文件），写上团队的编码规范——日志用什么库、错误怎么处理、命名风格是什么。不需要写得很完美，10-20 条规则就够了。关键是所有人用同一份，而不是各写各的。这个文件的 Owner 就是团队 Tech Lead，每次技术栈变化时更新。

第二，**一个 10 条用例的评估集**。从团队过去一个月的 AI 交互中，挑出 5 个"AI 做得好"的任务和 5 个"AI 做得差"的任务。记录输入和期望输出的特征。每次模型升级或规范修改时，在这 10 个用例上跑一遍，确认质量没有退化。不需要自动化——手动跑 10 个用例只需要 30 分钟。

第三，**每两周一次的 15 分钟规范复盘**。在团队的例会上加一个议题："AI 这两周有没有让你反复纠正的地方？"如果有，更新规范文件。如果没有，跳过。这个节奏足以让规范保持"活的"状态，不会腐烂。

这三样东西的总投入：初始设置 2 小时，持续维护每两周 30 分钟。回报是：AI 的输出风格在团队内一致、质量可追踪、规范不会腐烂。这就是小团队的 L2。

## 16.6 常见的失败模式

用反面案例强化一个认知：组织治理不是可选项。

开头的故事——日志规范混乱、Skill 散落各处、模型升级无人管理、记忆库无人清理——这些不是假设的场景，而是几乎每个引入 AI 编程的团队都会经历的阶段。它们背后是几种典型的失败模式。

最常见的是"无主资产"。Prompt 和 Skill 散落在各处——有的在项目仓库里，有的在某人的本地，有的在 Slack 消息里。没人知道哪个是最新的，没人负责更新，结果是 AI 的行为越来越不可预测。解法很简单：所有 AI 资产纳入版本控制，指定 Owner。

无主资产的自然后果是"评估缺位"——系统上线了但没有评估机制，团队只能靠"用户没投诉"来判断质量。直到有一天，一个 AI 生成的代码引入了一个隐蔽的 bug——它通过了代码审查（因为代码看起来很合理），但在特定的边界条件下会导致数据丢失。事后复盘发现，如果有评估集覆盖这类边界条件，这个问题本可以在上线前被发现。当你开始依赖 AI 的输出时，评估不是"有了更好"，而是必须的。

评估缺位又会导致"模型升级失控"——新模型一出就全量切换，没有灰度、没有回归、没有回滚计划。结果是一次升级导致大量任务的输出质量下降，团队花了一周时间排查问题、调整 Prompt、重新验证。如果有灰度机制，这个问题会在影响范围很小的时候就被发现。

还有一种结构性的失败："过度中心化"。所有 AI 相关的事都由一个"AI 团队"负责，业务团队提需求，AI 团队写 Skill、建评估、做优化。结果是 AI 团队不理解业务场景，写出来的 Skill 不贴合实际；业务团队不理解 AI 能力，提出的需求要么太简单要么太复杂。AI 的运营应该是嵌入式的——嵌入到每个业务团队中。

最后一种失败是"跳级建设"。团队还在 L0——个人随便用用 AI 对话工具——就开始建平台、搞多 Agent、上 RAG。基础设施搭了一大堆，但没人会用、没人维护。三个月后 RAG 的知识库过时了没人更新，MCP Server 挂了没人修，评估系统跑出来的数据没人看。先把 L1 和 L2 做扎实——让 Agent 跑起来、把规范建好，基础设施的需求会在使用中自然浮现，到那时再建也不迟。

---

到这里，我们已经把 AI 编程系统的所有工程化维度走了一遍——从系统蓝图到安全设计，从非确定性挑战到组织治理。这些章节回答的都是"怎么把 AI 编程用好"的问题。但还有一个更根本的问题一直悬在背后：AI 编程的能力边界到底在哪里？哪些事情它能越做越好，哪些事情它可能永远做不好？当这条技术曲线继续向前延伸，程序员的角色会怎么变化？
