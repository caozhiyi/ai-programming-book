# 10. 知识注入的三条路：RAG、微调与长上下文

你的 AI 编程助手什么都好，就是有一个致命的盲区：它不知道你公司的事。

你公司有一套内部的微服务框架，叫 `infra-go`。所有服务都基于这个框架搭建，它有自己的路由注册方式、中间件规范、配置加载机制、日志格式。这些信息写在内部的 Wiki 上，有几十页文档。

你让 AI 帮你用 `infra-go` 写一个新服务。它很努力，但它生成的代码用的是标准的 Gin 框架——因为它从未见过 `infra-go`。你告诉它"不要用 Gin，用 infra-go"，它道歉了，然后生成了一段看起来像是 `infra-go` 但实际上是它"猜"出来的代码——路由注册的 API 是错的，中间件的签名是错的，配置加载的方式也是错的。

它不是不聪明。它是真的不知道。

`infra-go` 的文档不在互联网上，不在任何公开的代码仓库里，不在模型的训练数据中。模型的训练数据有一个截止日期——在那个日期之后发布的信息，它不知道。而你公司的内部框架，无论什么时候发布的，都不会出现在公开的训练数据中。

这不是模型"不够聪明"的问题，而是模型"没见过"的问题。

怎么让模型知道它没见过的东西？这个问题有三种截然不同的回答方式。第一种：每次提问的时候，把相关的文档片段塞进上下文——"这是 infra-go 的路由注册文档，请基于这个文档生成代码。"这是 RAG（检索增强生成）的思路。第二种：用 `infra-go` 的文档和代码示例作为训练数据，对模型做一轮额外的训练，让它"学会" `infra-go`。这是微调的思路。第三种：把 `infra-go` 的全部文档一股脑塞进上下文窗口——反正现在的模型支持 128K 甚至更长的上下文。这是长上下文的思路。

三种方式都能让模型"知道" `infra-go`。但它们的原理不同、代价不同、适用场景不同。选错了方式，要么效果差，要么成本高，要么效果又差成本又高。

## 10.1 知识注入的根本需求

在展开三种方式之前，先理解它们要解决的是同一个问题。

大模型的知识来源只有两个：训练数据和上下文输入。训练数据决定了模型的"底层知识"——它在训练过程中见过的所有文本，经过参数化编码，变成了模型权重的一部分。当你问它"Go 的 goroutine 是什么"，它能回答，因为训练数据中有大量关于 Go 语言的内容。这些知识是"内化"的——不需要每次都提供，模型"天然就知道"。上下文输入决定了模型的"临时知识"——你在当前对话中提供的所有信息。当你把一段代码贴进对话框，模型就"知道"了这段代码的内容；当你让它联网搜索，搜索结果也会被塞进上下文——看起来模型"上网查了资料"，本质上只是多了一步自动检索，最终知识仍然是通过上下文窗口进入模型的。但这个"知道"是临时的——无论是你手动粘贴的代码还是搜索引擎返回的网页摘要，对话结束，这些信息就消失了。

问题出在两个地方。第一，训练数据有截止日期。模型的训练在某个时间点完成，之后发布的信息它不知道——上周发布的新版本、昨天更新的 API 文档、今天早上的安全公告，这些都不在模型的知识范围内。第二，训练数据不包含私有信息。你公司的内部文档、你项目的代码库、你团队的设计决策——这些信息从未出现在公开的互联网上，模型在训练时不可能见过。

这两个限制是根本性的。不管模型多大、训练数据多丰富，它都不可能知道"所有的事"——尤其是你的事。

三种知识注入方式，本质上是在不同的层面解决这个问题。**改变模型的输入**——RAG 和长上下文属于这一类。它们不改变模型本身，而是在每次调用时，把模型需要的知识放进上下文窗口。模型的权重没有变化，但它"看到"了新的信息，可以基于这些信息生成回答，相当于"临时告诉它"。**改变模型的权重**——微调属于这一类。它通过额外的训练，把新知识编码进模型的参数中。训练完成后，模型"天然就知道"这些知识，不需要每次都在上下文中提供，相当于"永久教会它"。

"临时告诉"和"永久教会"——这个区分是理解三种方式的关键。它决定了每种方式的优势、劣势和适用场景。

## 10.2 RAG：用检索弥补知识的不足

RAG 是目前最主流的知识注入方式。它的全称是 Retrieval-Augmented Generation——检索增强生成。名字很学术，但原理很直白。

**基本流程。**

RAG 的工作流程分四步。第一步，建立知识库——把你的文档（内部 Wiki、API 文档、设计文档、代码注释）切成小块，每块转换成一个向量（embedding），存入向量数据库，这是一个离线的、一次性的准备工作。第二步，接收用户查询——用户提出一个问题，比如"infra-go 的路由注册怎么写？"。第三步，检索相关文档——把用户的查询也转换成向量，在向量数据库中搜索和这个向量最相似的文档块，返回最相关的 3-5 个文档片段。第四步，注入上下文并生成——把检索到的文档片段塞进上下文窗口，和用户的查询一起发给模型，模型基于这些文档片段生成回答。

整个过程对用户来说是透明的——用户只是问了一个问题，系统在背后完成了检索和注入，用户看到的是一个"知道 infra-go"的 AI。

**向量嵌入的原理。**

RAG 的核心机制是"语义检索"——根据意思的相似度来查找文档，而不是根据关键词的匹配。这依赖于向量嵌入（embedding）技术。

向量嵌入做的事情是：把一段文本转换成一个高维空间中的点。这个"高维空间"通常有几百到几千个维度——远超人类能直观理解的三维空间，但数学上的操作方式是一样的。关键的性质是：语义相似的文本，在这个高维空间中的距离更近。"Go 的错误处理用 error 接口"和"Golang 中处理异常的方式是返回 error 类型"——这两句话的字面表达不同，但语义几乎一样，经过向量嵌入后，它们对应的两个点在高维空间中距离很近。而"Go 的错误处理用 error 接口"和"今天天气不错"——语义完全不同，对应的两个点距离很远。

这个性质让语义检索成为可能——把用户的查询转换成向量，在知识库中找到距离最近的几个文档块，这些文档块大概率就是和查询语义最相关的内容。向量嵌入是怎么做到这一点的？简单来说，嵌入模型在训练过程中"学会"了语言的语义结构——它知道"错误处理"和"异常处理"是相近的概念，知道"Go"和"Golang"指的是同一个东西，知道"返回 error"和"用 error 接口"描述的是同一种模式。这些语义关系被编码在向量的数值中。你不需要理解向量嵌入的数学细节，你需要理解的是：它让计算机能够按"意思"而不是按"字面"来比较文本。这是 RAG 能够工作的基础。

**分块策略：RAG 质量的关键。**

知识库中的文档需要被切成小块才能存入向量数据库。这个"切"的过程叫分块（chunking），它对 RAG 的质量有决定性的影响。为什么要切？因为向量嵌入对文本长度有限制——太长的文本，嵌入模型无法有效地把它压缩成一个向量。而且太长的文档块在检索时精度低——一个 5000 字的文档块中可能只有一段话和查询相关，但整个块都会被返回，浪费上下文空间。

切多大？这是一个核心的权衡。块太大，检索精度低——一个 2000 Token 的块中，可能只有 200 Token 是和查询相关的，剩下的 1800 Token 是噪声，而且大块的向量表示会"平均化"，块中不同部分的语义被混合在一起，导致向量不能精确地代表块中任何一个具体的信息点。块太小，上下文丢失——一句话"TTL 设置为 300 秒"，如果脱离了上下文，你不知道这是 Redis 缓存的 TTL、DNS 记录的 TTL、还是 HTTP 缓存的 TTL。小块保留了精确的信息点，但丢失了理解这个信息点所需的上下文。

实践中常用的块大小在 200-1000 Token 之间，具体取决于文档的类型和结构。对于代码文件，按语义边界切分通常比按固定大小切分效果更好——按函数、按类、按模块切分，每个块是一个语义完整的单元。对于技术文档，按章节或段落切分通常是合理的——每个章节讨论一个主题，是一个自然的语义单元。还有一种策略是"重叠切分"——相邻的块之间有一定的重叠，比如块大小是 500 Token，重叠是 100 Token，这样每个块的开头包含了上一个块结尾的内容，减少了在块边界处丢失上下文的问题。

**RAG 的优势。**

RAG 之所以成为最主流的知识注入方式，根本原因在于它不改变模型本身——模型的权重不变，只是每次调用时"看到"了新的信息。这意味着知识库可以随时更新（改文档、重新生成向量，几分钟搞定），同一个模型可以对接不同的知识库（对接内部文档就变成"懂公司业务的 AI"，对接代码库就变成"懂项目代码的 AI"），而且每一条信息都可以追溯到具体的文档和段落——如果 AI 的回答有误，你可以检查它引用了哪些文档，判断是文档本身有问题还是模型的理解有问题。这种可追溯性在企业场景中非常重要。

## 10.3 RAG 的常见失败模式

RAG 的原理很优雅，但实践中的效果参差不齐。很多团队搭建了 RAG 系统后发现，AI 的回答质量并没有显著提升——有时候甚至变差了。这不是 RAG 的原理有问题，而是 RAG 的每一个环节都可能出错。

**失败模式一：检索不到。** 知识库里明明有答案，但检索没找到。最常见的原因是查询和文档的"表达方式"差异太大——用户问"怎么在 infra-go 里注册路由"，但文档里写的是"HTTP Handler 的绑定方式"。语义上是同一件事，但嵌入模型可能没有学到"注册路由"和"Handler 绑定"之间的等价关系，尤其是当这些术语是你公司内部特有的表达方式时。通用的嵌入模型是在公开的互联网文本上训练的，它对通用术语的语义理解很好，但对领域特定的术语可能不够敏感。另一个原因是分块不合理——如果答案跨越了两个块的边界，前半部分在第 N 块的结尾，后半部分在第 N+1 块的开头，那么两个块单独检索时都不会被认为是高度相关的，因为每个块只包含了答案的一半。

**失败模式二：检索到但不相关。** 检索返回了结果，但这些结果和用户的实际需求不匹配。这种情况通常发生在查询比较模糊或者知识库中有大量"表面相似但实际不同"的内容时。你搜"缓存的配置方式"，返回了 Redis 缓存的配置、HTTP 缓存的配置、DNS 缓存的配置——它们都和"缓存配置"语义相似，但你实际上只需要 Redis 缓存的配置。语义检索只看"意思像不像"，不看"是不是你要的那个"，它无法区分"同一个概念在不同上下文中的不同含义"。

**失败模式三：检索到但模型忽略了。** 这是最隐蔽的失败模式。检索结果是正确的，也被成功注入了上下文，但模型在生成回答时忽略了它。一个常见的原因是 Lost in the Middle——检索结果被放在了上下文的中间位置，模型的注意力没有充分关注到它，上一章详细讨论过这个问题。另一个原因更微妙：模型的"先验知识"和检索结果冲突。模型在训练时学到了"Go 的 HTTP 路由通常用 `http.HandleFunc` 或 Gin 的 `router.GET`"，而检索结果告诉它"infra-go 用 `app.bindHandler` 注册路由"。当先验知识和上下文信息冲突时，模型可能会"倾向于"自己的先验知识——尤其是当检索结果的表述不够清晰或权威时。这就像一个经验丰富的程序员，你给他一份内部框架的文档，但他"习惯性地"按照自己熟悉的方式写代码，忽略了文档中的特殊要求。

**失败模式四：信息不完整。** 分块太小导致检索到的片段缺乏必要的上下文。检索返回了一个代码片段：`app.bindHandler("/users", userHandler, middleware.Auth())`。这个片段本身是正确的，但它缺少了关键的上下文——`userHandler` 应该是什么类型？`middleware.Auth()` 的参数是什么？`app` 是怎么初始化的？模型基于这个不完整的片段生成代码，可能会"猜"错 `userHandler` 的类型签名，或者用错误的方式初始化 `app`。

**应对思路。** 每种失败模式都有对应的改善方向，但没有一种是"配置一下就好了"的简单操作。检索不到，可以改善分块策略（确保答案不会被切断）、使用混合检索（语义检索 + 关键词检索互补）、对查询做改写（把用户的查询扩展成多种表达方式，增加命中概率）。检索到但不相关，可以增加元数据过滤（比如按项目、按模块过滤，缩小检索范围）、提高嵌入模型的领域适应性。检索到但被忽略，可以调整注入位置（把检索结果放在上下文的开头或结尾，而不是中间）、在 System Prompt 中明确指示"请优先参考提供的文档内容"。信息不完整，可以增大块的大小或使用重叠切分、在检索到某个块后自动扩展上下文（把相邻的块也一起返回）。

每一个改善方向都涉及权衡——增大块的大小会降低检索精度，混合检索会增加计算成本，查询改写会增加延迟。RAG 的调优是一个持续的、需要根据实际效果不断迭代的过程。

## 10.4 微调：改变模型的权重

RAG 是"临时告诉"模型它不知道的事。微调是"永久教会"模型它不知道的事。

**微调的本质。** 微调（Fine-tuning）是在预训练模型的基础上，用特定领域的数据继续训练，训练的结果是模型的权重发生了变化——新的知识和行为模式被编码进了参数中。打个比方：预训练模型像一个刚从大学毕业的通才——什么都知道一点，但对任何特定领域都不够深入。微调像是让这个通才在某个公司实习了三个月——他学会了公司的内部术语、工作流程、代码规范。实习结束后，这些知识变成了他的"本能"——不需要每次都翻文档，他"自然就知道"该怎么做。微调后的模型，在处理特定领域的任务时，不需要在上下文中提供额外的知识——知识已经在权重里了。

**微调适合什么。** 微调最擅长的是改变模型的"行为模式"——让它学会一种特定的输出风格、格式或思维方式。比如输出格式：你希望模型生成的代码始终遵循特定的格式——每个函数都有标准的注释模板、错误处理都用特定的包装方式、日志都用特定的格式，通过微调，模型可以"内化"这些格式要求，不需要每次都在 Prompt 中说明。比如领域术语：你的行业有大量的专有术语，通用模型可能不理解或者理解不准确，通过微调，模型可以学会这些术语的正确含义和用法。比如推理模式：你希望模型在面对特定类型的问题时，按照特定的步骤来分析——遇到性能问题时先检查算法复杂度、再检查 I/O 瓶颈、再检查内存分配，微调可以让模型学会这种领域特定的推理模式。

**微调不适合什么。** 微调不擅长的是记忆大量的事实性知识。你不应该用微调来让模型"记住"你公司所有 API 的参数列表——模型的参数不是数据库，它不擅长精确地存储和检索结构化数据。即使你用 API 文档做了微调，模型也可能在具体的参数名称、类型、默认值上出错，因为这些精确的细节在参数化编码的过程中容易被"模糊化"。你也不应该用微调来注入频繁更新的知识——API 文档每周都在更新，如果每次更新都要重新微调，成本和周期都不可接受，微调一次可能需要几个小时到几天的时间，而且需要 GPU 资源。

一个简单的判断标准：**如果这个知识可以用一句话描述，而且不经常变化，微调可能合适。如果这个知识需要一整页文档来描述，或者经常变化，RAG 更合适。** "代码中的错误处理应该用 `fmt.Errorf` 包装"——这是一个行为模式，适合微调。"UserService 的 CreateUser 方法接受 username(string)、email(string)、role(enum: admin|user|guest) 三个参数，返回 UserID(int64) 和 error"——这是一个事实性知识，适合 RAG。

**微调的代价。** 微调不是免费的午餐。它需要高质量的训练数据——"高质量"意味着数据要准确、格式要一致、覆盖面要广，准备训练数据本身就是一项耗时的工作，你需要从内部文档中提取问答对、从代码库中提取示例、从团队的最佳实践中提取模式，数据质量直接决定了微调的效果——垃圾进，垃圾出。它需要计算资源——微调需要 GPU，而且通常需要多张 GPU，即使使用参数高效的微调方法（只调整模型的一小部分参数），也需要相当的计算资源。训练周期长——从准备数据到训练完成到评估效果，一个完整的微调周期可能需要几天到几周，如果效果不理想，需要调整数据和参数重新训练，周期更长。容易过拟合——如果训练数据太少或者太单一，模型可能会"过度适应"训练数据，在训练数据覆盖的场景下表现很好，但在稍有不同的场景下表现反而变差。更新慢——每次知识更新都需要重新训练，如果你的知识库每天都在变化，微调的更新速度跟不上。

回到 10.1 提出的区分——微调是"永久教会"，RAG 是"临时告诉"。两者不是竞争关系，而是互补关系。你完全可以用微调让模型学会你的编码风格和领域术语（改变"性格"），同时用 RAG 让模型在每次任务中获取最新的文档和代码（提供"见闻"）。微调提供"底层能力"，RAG 提供"实时知识"——两者在不同的层面发挥作用。

RAG 需要建立知识库、设计分块策略、部署向量数据库。微调需要准备训练数据、配置训练环境、等待训练完成。有没有更简单的方式？

有。把所有文档直接塞进上下文窗口。

现在的模型支持越来越长的上下文——128K Token、200K Token、甚至更长。128K Token 大约相当于一本 300 页的书。如果你的内部文档总量不超过这个限制，理论上可以把所有文档一次性塞进上下文，让模型直接"看到"所有内容。不需要向量数据库，不需要分块策略，不需要检索算法，不需要训练环境。只需要把文档拼接成一个长字符串，放进上下文窗口。

**为什么它有吸引力。** 长上下文方案的最大优势是实现简单——不需要任何额外的基础设施，没有向量数据库要维护，没有嵌入模型要选择，没有分块策略要调优，对于小团队或者快速原型来说，这种简单性非常有价值。其次是信息完整——RAG 的分块过程不可避免地会丢失跨块的上下文关系，长上下文不需要分块，所有信息都在一个完整的上下文中，模型可以看到文档的全貌，理解不同部分之间的关联。最后是没有检索失败的问题——RAG 的检索可能找不到相关文档、可能找到不相关的文档，长上下文不需要检索，所有文档都在上下文里，模型自己去找需要的信息。

**为什么它不是万能的。** 长上下文的第一个问题是成本高——上下文越长，Token 消耗越大。如果你的文档有 100K Token，每次调用都要传输这 100K Token 的输入，一天调用 100 次就是 1000 万 Token 的输入，光是文档部分的成本就相当可观，而且这些文档在每次调用中都是一样的，但每次都要重新传输和处理（除非使用上一章讨论的 Prompt Caching）。第二个问题是注意力衰减——上一章详细讨论过 Lost in the Middle 现象，上下文越长，模型对中间位置信息的关注度越低。把 100K Token 的文档塞进上下文，模型对文档中间部分的信息可能关注不足，你需要的那个 API 参数说明恰好在文档的中间位置，模型可能就"看漏"了。RAG 通过检索，把最相关的信息"提取"出来放在显眼的位置——这实际上是在帮模型"聚焦"，长上下文没有这个聚焦机制。第三个问题是延迟高——Transformer 的注意力计算复杂度是 O(n²)，上下文长度翻倍，计算量翻四倍，128K Token 的上下文推理时间可能是 4K Token 的上千倍，在实时交互场景中这种延迟可能是不可接受的。第四个问题是容量有限——128K Token 听起来很多，但对于一个真实的项目来说可能远远不够，一个中等规模的代码库可能有几十万行代码，远超任何模型的上下文窗口。

简单来说，长上下文适合信息量不大但需要完整性的场景——分析一个完整的配置文件、审查一个中等大小的代码文件、理解一份完整的设计文档。它也适合快速原型验证——在项目早期，你还不确定 RAG 是否值得投入，先用长上下文做一个快速验证，效果好再考虑用 RAG 优化成本。它不适合的场景——信息量巨大、高频调用、需要精确定位——恰好是 RAG 擅长的领域。

## 10.6 三条路的选型判断

前面三节分别拆解了每种方式的原理和局限。选型不需要把所有优劣重新过一遍——你只需要回答三个问题。

![三种知识注入方式的选型判断](images/10-knowledge-injection-decision.svg)

**第一问：这个知识需要多频繁更新？** 高频更新（每天、每周）直接选 RAG——改文档、重新生成向量，几分钟搞定，微调的训练周期根本跟不上。低频更新（每月、每季度）微调才是可选项。一次性的知识（一份特定的文档、一个特定的代码文件）用长上下文最简单——不需要建知识库，不需要训练，直接塞进去。

**第二问：这个知识是事实还是模式？** 事实性知识（API 参数、配置选项、数据结构）选 RAG——模型的参数不擅长精确记忆这类细节。行为模式（编码风格、输出格式、推理步骤）选微调——这类知识需要"内化"成模型的行为习惯。完整的上下文（一份完整的文档、一个完整的文件）选长上下文——分块会破坏信息的连贯性。

**第三问：信息量有多大？** 几千到几万 Token，长上下文最简单。几万到几十万 Token，RAG 是最佳选择。几十万 Token 以上，只有 RAG 能处理。三个问题的答案基本决定了方案选择。

**组合使用。** 在实际的系统中，三种方式经常被组合使用。一个典型的组合是：用微调让模型学会公司的编码规范和领域术语，用 RAG 在每次任务中注入最新的 API 文档和设计文档，用长上下文处理当前正在编辑的代码文件。微调提供"底层能力"，RAG 提供"实时知识"，长上下文提供"当前上下文"——三者共同构成一个完整的知识注入体系。

用一个类比来总结：RAG 像是一个实时查询数据库的系统——每次请求都去查最新的数据，结果总是最新的，但每次都有查询的开销。微调像是编译时优化——提前把知识"编译"进模型，运行时不需要额外的查询，但更新需要重新"编译"。长上下文像是把整个数据库加载到内存——简单直接，所有数据都在手边，但内存（上下文窗口）是有限的，而且加载的数据越多，处理速度越慢。

卷三到这里就结束了。

我们解决了"信息"层面的问题——记忆、上下文、知识注入，让 AI 拥有足够的信息来完成任务。

但有了信息不等于能做出好的决策。你的 AI 编程助手可能拥有项目的所有知识，但当你问它"这个新功能应该用微服务还是放在现有的单体里"，它给出的建议可能仍然不靠谱——因为这个决策涉及的不只是技术知识，还有团队规模、交付时间、运维能力这些模型难以量化的维度。怎么在 AI 的帮助下做出更好的技术决策？什么样的决策适合交给 AI，什么样的决策必须人来做？这些问题定义了下一个层次——从"能做事"到"做对事"。
