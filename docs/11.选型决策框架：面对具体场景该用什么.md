# 11. 选型决策框架：面对具体场景该用什么

你的团队刚接手一个任务：为公司的内部运维平台添加一个"智能诊断"功能——用户描述一个线上问题，AI 自动查询监控数据、分析日志、定位根因、给出修复建议。

团队开了一个技术方案评审会。方案一："我们用 MCP 接入 Prometheus、Elasticsearch、Kubernetes API，再用一个 SubAgent 架构——一个 Agent 负责查询监控，一个负责分析日志，一个负责综合诊断，最后用一个协调 Agent 汇总结果。Skill 用来定义诊断流程和输出规范。"方案二："我们先用一个 Agent，System Prompt 里写清楚诊断流程，内置几个工具函数直接调用 Prometheus 和 ES 的 API。先跑起来看看效果，不够再加。"

方案一听起来更"专业"。方案二听起来更"简陋"。

但如果你读过前面的章节，你会先问一个问题：这个场景的实际约束是什么？内部运维平台日活几十人，不需要高并发；每次诊断查询几次 API，不是每秒几十次；这些工具只在这个平台用，不需要跨平台复用；查询监控、分析日志、综合诊断是有先后依赖的（先查数据才能分析），不是可以并行的独立任务。

在这些约束下，方案一的每一个"高级"组件都值得质疑：MCP 的标准化在这里没有价值（不需要跨平台），SubAgent 的并行化在这里没有收益（任务是线性的），协调 Agent 增加了一层不必要的复杂度。方案二可能是更好的起点。

这不是说方案一永远是错的——如果约束条件变了（比如这些工具需要被多个平台使用，比如子任务可以并行），方案一的组件就有了存在的理由。判断力不是"知道哪个方案更好"，而是"知道在什么条件下哪个方案更好"。

前三卷建立了一个完整的工具箱——大模型的原理、Agent 的执行机制、MCP 和 Skill 的扩展方式、多 Agent 的协作模式、记忆体系、上下文工程、知识注入。工具箱满了，但工具箱满不等于每个任务都要把所有工具拿出来用。

## 11.1 直接对话 vs Agent：什么时候需要自主执行能力

第一个判断：这个任务需要 Agent 吗？

这个问题听起来简单，但在实践中经常被跳过。很多人的默认思路是"用 Agent 肯定比直接对话好"——Agent 能自主执行、能调用工具、能多步推理，看起来是直接对话的"升级版"。但 Agent 不是直接对话的升级版。它们是不同的工具，适用于不同的场景。

**直接对话能做什么。**

直接对话——就是你在聊天窗口里和模型一问一答——能做的事情比很多人以为的要多。代码解释（"这段代码在做什么？"）、概念问答（"Go 的 channel 和 mutex 什么时候该用哪个？"）、单文件代码生成（"帮我写一个 HTTP 中间件，记录请求的耗时和状态码"）、单文件代码审查（"看看这段代码有什么问题"）、方案讨论（"这个功能用消息队列还是直接 RPC 调用？"）——这些任务都可以在直接对话中高质量地完成。

这些场景有一个共同特征：**所有需要的信息要么在模型的训练数据中，要么在你提供的上下文中。** 模型不需要"走出去"获取额外的信息，也不需要执行任何操作来改变外部世界的状态。你把代码贴进去，模型解释给你听；你描述需求，模型生成代码；你提出问题，模型基于已有知识回答。整个过程是自包含的——输入和输出都在对话窗口内完成。在这些场景下使用 Agent，不会让结果更好——只会让过程更慢、更贵、更容易出错。

**Agent 能做什么是直接对话做不到的。**

Agent 的核心能力是"自主执行"——它可以调用工具、读取文件、搜索代码、执行命令，然后根据结果决定下一步做什么。考虑跨文件重构的场景："把项目中所有使用旧版日志库的地方迁移到新版日志库。"Agent 需要搜索整个代码库找到所有使用旧版日志库的文件，理解每个文件的上下文，生成修改方案，可能还需要运行测试来验证修改没有破坏功能。这个任务涉及多个文件、多个步骤、需要根据中间结果调整策略——你不可能把整个代码库贴进聊天窗口。类似的还有自动化测试生成（需要读取源代码、理解函数签名、参考已有测试风格、运行验证）和代码库级别的问题诊断（需要查看 commit 记录、分析变更代码、读取监控数据、定位可疑变更）。

这些场景的共同特征是：**任务需要的信息分散在多个地方，需要通过工具交互来获取；任务的执行需要多个步骤，后续步骤依赖前面步骤的结果。**

**过度使用 Agent 的代价。**

Agent 不是免费的。一个简单的代码解释任务，直接对话可能只需要 2K Token、2 秒返回结果。用 Agent 做同样的事，它会先搜索代码库、读取相关文件、分析依赖关系，然后才开始解释——可能需要 20K Token、30 秒到几分钟。而且 Agent 的每一步都可能出错，步骤越多出错的概率越高，第 8 步出错意味着前面 7 步的工作全部白费。

**一个简单的判断规则。**

问自己一个问题：**这个任务能在一次对话中完成吗？** "一次对话"的意思是：你能把所有需要的信息放进上下文（通过复制粘贴或者其他方式），模型能在一次回复中给出完整的答案。如果能——用直接对话，更快、更便宜、更可控。如果不能——因为信息分散在多个文件中、因为需要执行命令来获取信息、因为任务需要多个步骤——那就需要 Agent。

这个判断规则不是绝对的，但它是一个好的起点。它的核心思想是：**不要为了用 Agent 而用 Agent。先考虑最简单的方式，只有当最简单的方式明确不够用时，才升级到更复杂的方式。**

## 11.2 单 Agent vs 多 Agent：什么时候需要拆分

确定了需要 Agent 之后，下一个判断：需要几个 Agent？

第六章详细讨论了多 Agent 的协作模式——管道模式、分治模式、辩论模式、监督模式。这些模式很有吸引力，但多 Agent 不是"更多就更好"。

**"任务复杂"不等于"需要多 Agent"。**

这是最常见的误判。很多人的逻辑是："这个任务很复杂，一个 Agent 搞不定，所以需要多个 Agent。"但"复杂"有不同的含义。

一种复杂是"步骤多"——任务需要很多步骤才能完成，但每一步的性质是相似的。比如"重构项目中所有的错误处理"——需要找到所有相关的文件、逐个修改、逐个验证。步骤很多，但每一步都是"读代码→理解→修改→验证"的相同模式。这种复杂不需要多 Agent——一个 Agent 按顺序执行就行。另一种复杂是"角色多"——任务需要不同的专业视角。比如"设计一个新的 API 并实现它"——需要一个角色从 API 设计的角度考虑接口的一致性和易用性，需要另一个角色从实现的角度考虑性能和可维护性，需要第三个角色从测试的角度考虑边界情况和异常处理。这种复杂可能需要多 Agent——因为不同的角色需要不同的 System Prompt、不同的工具集、不同的评判标准。

判断标准不是"任务有多难"，而是"任务是否需要不同的专业角色"。

**多 Agent 真正有价值的两个场景。**

第一个场景是可并行的独立子任务。你让 AI 分析一个项目的代码质量，分析包括检查代码风格、检查测试覆盖率、检查依赖安全性、检查 API 文档完整性。这四个子任务是完全独立的——检查代码风格不需要知道测试覆盖率的结果，检查依赖安全性不需要知道 API 文档的状况。如果用单 Agent 串行执行，假设每个子任务需要 30 秒，总共需要 120 秒；如果用 SubAgent 并行执行，四个子任务同时进行，总共只需要 30 秒。4 倍的速度提升——但前提是子任务之间必须是独立的。如果子任务 B 需要子任务 A 的结果才能开始，它们就不能并行，SubAgent 的优势就不存在了。

第二个场景是需要上下文隔离的专业分工。你让 AI 完成一个完整的功能开发——写代码、写测试、做代码审查。用单 Agent 做这三件事有一个微妙的问题：Agent 在写代码时建立的"思维惯性"会影响它写测试和做审查的质量。它刚写完一段代码，对这段代码有"先入为主"的理解——测试倾向于验证"代码做了什么"而不是"代码应该做什么"，审查倾向于忽略自己代码中的问题。这不是 AI 的"偏见"——这是上下文的物理效应，写代码时的上下文（设计思路、实现细节）会影响后续任务的生成方向。用 SubAgent 分工可以缓解这个问题：写代码的 Agent 上下文只包含需求和设计，写测试的 Agent 上下文只包含需求和接口定义（不包含实现细节），审查的 Agent 上下文包含代码和审查规范。每个 Agent 有独立的上下文，不会被其他任务的"思维惯性"污染。

**多 Agent 不该用的两个场景。**

第一个是简单的线性任务。你让 AI 帮你写一个 CRUD 接口——定义数据模型、写数据库操作、写 HTTP Handler、写路由注册。这四个步骤是严格线性的：数据模型定义好了才能写数据库操作，数据库操作写好了才能写 Handler。在这种场景下引入 SubAgent，你需要一个协调 Agent 来管理执行顺序，每次传递都有信息损失的风险。而且每个 SubAgent 都有自己的上下文初始化开销，四个 SubAgent 的初始化开销加起来可能比单 Agent 直接串行执行还慢。更重要的是，单 Agent 在串行执行时有一个天然的优势：**完整的上下文连续性。** 它在写数据模型时建立的理解会自然地延续到写数据库操作、写 Handler 的过程中，这种连续性在 SubAgent 架构中需要通过显式的信息传递来维持——而显式传递总是不如隐式延续完整。

第二个是子任务之间强耦合的场景。你让 AI 重构一个模块——修改数据结构、更新所有使用这个数据结构的函数、修改相关的测试。表面上看这三个子任务可以分给三个 SubAgent，但实际上它们之间有强耦合：修改数据结构的方式决定了函数怎么更新，函数的更新方式决定了测试怎么修改。如果三个 SubAgent 各自独立工作，它们的输出很可能不一致——数据结构改了字段名，但函数还在用旧的字段名。要解决这个一致性问题，SubAgent 之间需要频繁通信，这种通信的开销和复杂度会迅速增长。一个判断标准：**如果子任务之间的通信量接近或超过子任务本身的工作量，SubAgent 就不值得引入。**

**多 Agent 的隐性成本。**

多 Agent 带来的隐性成本往往被低估。最直观的是 Token 成本倍增——每个 Agent 都有自己的 System Prompt、自己的上下文、自己的推理过程，3 个 Agent 的 Token 消耗通常是 1 个 Agent 的 5-10 倍。但更隐蔽的成本是信息损耗：Agent 之间的通信通常是通过文本，一个 Agent 在推理过程中建立的"隐性理解"无法通过文本完整传递，信息在传递过程中不可避免地会丢失。再加上协调逻辑本身的复杂度——谁先执行、谁后执行、失败了怎么回滚——多 Agent 系统的调试难度远超单 Agent，因为问题可能出在任何一个环节。

先尝试单 Agent。只有当单 Agent 明确撑不住时——角色冲突导致输出质量下降、上下文溢出导致信息丢失、串行执行导致时间不可接受——才考虑多 Agent。多 Agent 是一个"不得已"的选择，不是一个"更高级"的选择。**SubAgent 的价值和"可并行度 × 任务复杂度"成正比。** 高并行度、高复杂度的任务，SubAgent 的收益最大。低并行度或低复杂度的任务，协调开销会吞噬收益。

## 11.3 MCP vs Skill vs 内置工具：能力扩展的三条路

确定了 Agent 的数量之后，下一个判断：Agent 的能力扩展该用什么方式？

前面的章节分别讨论了 MCP（第四章）、Skill（第五章）和内置工具的原理。它们都是给 Agent 增加能力的方式，但解决的问题不同。一个简单的判断方式：**如果你需要 Agent "做一件事"，用工具（内置或 MCP）。如果你需要 Agent "按某种方式做所有事"，用 Skill。**

**内置工具：高频核心操作。**

内置工具是 AI 编程助手"出厂自带"的能力——读文件、写文件、搜索代码、执行终端命令、浏览网页。这些工具直接集成在 Agent 的运行时中，调用延迟最低、稳定性最高。读写文件是几乎每个编程任务都需要的操作，Agent 每个任务可能执行几十次，延迟要求高（每次读文件如果要等 2 秒，10 次就是 20 秒），而且所有项目都需要。这些操作不需要标准化（只在本地执行），不需要跨平台（只在当前 IDE 中使用），不需要动态发现（Agent 启动时就知道有哪些工具）。内置工具的局限是灵活性低——你不能轻易地添加新的内置工具，也不能根据项目的需求定制内置工具的行为。

**MCP：标准化的外部工具集成。**

MCP 的核心价值是标准化——用统一的协议连接不同的外部工具和服务。理解 MCP 的价值，关键是理解它解决的"乘法问题"。你的 AI 编程助手需要查询 Jira 上的 Issue、读取 Confluence 上的文档、操作 GitHub 上的 PR。这三个系统各自有自己的 API——不同的认证方式、不同的请求格式、不同的响应结构。如果你为每个 AI 工具（Cursor、Copilot、你自己的 Agent）分别实现这三个系统的集成，你需要写 3 × 3 = 9 套集成代码。MCP 把这个问题变成了 3 + 3：写 3 个 MCP Server，3 个 AI 工具各自实现 MCP Client，任何一个 AI 工具都可以通过 MCP 协议调用任何一个 Server。**标准化降低了集成的边际成本**——第一个 MCP Server 的开发成本和直接写 API 调用差不多，但从第二个开始，边际成本急剧下降。

这个价值在工具生态快速变化的当下尤其重要。今天你用 Cursor，明天可能换成另一个工具。如果你的工具集成是通过 MCP 实现的，迁移成本几乎为零——新工具只要支持 MCP 就能直接使用你已有的所有 Server。而且 MCP 的工具发现机制（`tools/list`）让 AI 能在运行时知道有哪些工具可用，你可以动态地添加新的 MCP Server，AI 不需要任何代码修改就能使用新工具。

但 MCP 不是万能的。它基于 JSON-RPC 协议，每次调用都有序列化/反序列化的开销，如果是远程 Server 还有网络往返的延迟。对于大多数 AI 编程场景，这个开销可以忽略——查询一次数据库、调用一次 API，几十毫秒的协议开销相对于几百毫秒的模型推理时间微不足道。但如果你的场景需要高频调用——比如一个代码分析工具需要对每一行代码都调用一次 AST 解析服务，每次分析涉及几千次调用——MCP 的协议开销就会累积成显著的性能瓶颈。这种场景下，直接在进程内调用工具函数比通过 MCP 协议调用高效得多。另一个不该用 MCP 的场景是简单的内部专用工具——你写了一个小工具读取项目的 `go.mod` 文件并列出所有依赖，只在你的一个项目里用，只在 Cursor 里用。把它包装成 MCP Server 需要定义 JSON Schema、实现 JSON-RPC 处理、处理连接管理、写配置文件——这些"标准化"的工作量可能比工具本身的逻辑还多。直接写一个内置工具函数，可能只需要 20 行代码。

**MCP 的价值和"复用次数"成正比。** 一个 MCP Server 被 5 个平台使用，标准化的投入就值了。一个 MCP Server 只被 1 个平台使用，标准化的投入就是浪费。

**Skill：领域知识和工作流注入。**

Skill 和 MCP、内置工具有本质的不同——MCP 和内置工具给 Agent 增加的是"能做什么"（能力），Skill 给 Agent 增加的是"该怎么做"（知识和流程）。Skill 的核心价值是**把领域知识和流程约束从临时的提示词中提取出来，变成可复用的、可版本化的资产**。

Skill 最适合两类场景。第一类是领域知识注入——你的团队有一套编码规范（命名规则、错误处理方式、日志格式、测试策略），你希望 AI 在生成代码时遵循这些规范。你可以每次都在提示词里写一遍，但这种方式是临时的、不可复用的、容易遗漏的。把规范封装成 Skill，团队所有人加载同一个 Skill，AI 的行为就是一致的，不依赖每个人的提示词写作能力；规范更新了修改 Skill 文件就行，所有人下次加载时自动获取最新版本。第二类是流程标准化——你的团队有一套代码审查流程（先检查功能正确性，再检查错误处理，再检查性能影响，再检查安全风险）。如果你只是在提示词里说"请审查这段代码"，AI 可能会随机地关注某些方面而忽略其他方面。把审查流程封装成 Skill，明确定义每个步骤的检查内容和输出格式，AI 每次审查都会按照同样的流程执行。这不是限制 AI 的灵活性——这是确保 AI 不会遗漏关键步骤。

但 Skill 是预定义的——它在任务开始之前就确定了 AI 应该遵循的规则和流程。在需要根据运行时情况灵活调整策略的场景下，预定义的 Skill 会变得僵硬。比如你想让 AI 帮你重构一个大型项目，重构的策略取决于代码的实际状况——耦合度高应该先解耦，测试覆盖率低应该先补测试，技术债务多应该先清理。你很难用一个预定义的 Skill 覆盖所有这些情况，如果你试图穷举所有可能的策略和分支，本质上你是在 Skill 里写了一个"决策引擎"，这违背了 Skill 的设计初衷。这种场景更适合直接在提示词中描述当前的具体情况让 AI 根据上下文做出判断。

另一个需要注意的问题是上下文膨胀。每个 Skill 被加载后它的内容会占用上下文空间——一个编码规范 Skill 可能占 2000 Token，一个审查流程 Skill 可能占 1500 Token。如果你同时加载了 5 个 Skill，可能就占了 8000-10000 Token。对于一个 128K 上下文窗口的模型，10000 Token 看起来不多，但别忘了上下文中还有 System Prompt、对话历史、代码文件、工具调用结果，实际留给 Skill 的空间可能比你想象的少得多。而且 Skill 越多 Lost in the Middle 效应越明显——AI 可能会"遗忘"中间位置的某些 Skill 内容。一个实用的原则：**每次只加载当前任务最相关的 Skill。**

**Skill 的价值和"复用次数 × 标准化需求"成正比。** 一个 Skill 被 10 个人在 100 次任务中使用，封装的投入就值了。一个 Skill 只被你自己用一次，封装的投入就是浪费。

## 11.4 组合使用的设计模式

前面三节分别讨论了直接对话 vs Agent、单 Agent vs 多 Agent、MCP vs Skill vs 内置工具的独立判断。但在真实的工程实践中，这些组件经常需要组合使用。组合不是随意的——有一些经过验证的模式。

**模式一：Skill 定义规范 + MCP 提供工具 + 单 Agent 执行。**

这是最常见的组合，适合大多数中等复杂度的任务。以 AI 辅助代码审查为例：Skill 定义审查规范（检查哪些维度、每个维度的检查标准、输出格式），MCP 提供工具（读取 Git diff、查询 CI 构建结果、获取相关的设计文档、查询历史 Issue），单 Agent 加载审查 Skill、使用 MCP 工具获取必要的信息、按照 Skill 定义的流程执行审查、输出结构化的审查报告。这个组合的优势在于职责清晰：Skill 管"怎么做"（流程和标准），MCP 管"用什么做"（工具和数据），Agent 管"执行"，三者各司其职互不干扰。

**模式二：主 Agent 规划 + SubAgent 并行执行 + MCP 工具。**

这个组合适合可并行化的复杂任务。以 AI 辅助项目健康度评估为例：主 Agent 接收"评估项目健康度"的任务，分解为几个独立的子任务——代码质量分析、依赖安全检查、测试覆盖率评估、文档完整性检查。每个 SubAgent 负责一个子任务并使用 MCP 工具访问相应的外部服务。四个 SubAgent 并行执行各自产出子报告，主 Agent 汇总四份子报告生成综合评估。优势在于速度——四个子任务并行执行，总耗时取决于最慢的那个而不是四个的总和。

**模式三：Skill 定义规范 + SubAgent 分别执行"写"和"审"。**

这个组合适合需要"生产"和"质检"分离的场景。写代码的 SubAgent 加载编码规范 Skill，根据需求生成代码；审查代码的 SubAgent 加载审查规范 Skill，审查第一个 SubAgent 生成的代码——上下文包含代码和审查规范，但不包含第一个 SubAgent 的"思考过程"。审查 Agent 没有被写代码 Agent 的"思维惯性"污染，它能更客观地发现问题。如果审查 Agent 发现了问题，可以把反馈传回给写代码的 Agent 让它修复，形成一个"写→审→改→再审"的循环直到审查通过。

**组合的原则。**

组合不是越多越好——每增加一个组件都要问两个问题。**它解决了什么问题？** 如果你说不清楚一个组件解决了什么具体的问题，它大概率是不需要的。"MCP 让工具标准化了"——但如果工具只在一个地方用，标准化解决了什么问题？"SubAgent 让任务并行了"——但如果任务是线性的，并行化解决了什么问题？**它引入了什么成本？** 每个组件都有成本——MCP 引入了协议开销和 Server 管理成本，Skill 引入了上下文空间占用和维护成本，SubAgent 引入了协调开销和一致性风险。只有当"解决的问题"的价值大于"引入的成本"时，这个组件才值得加入。

一个反模式值得警惕："我们的系统应该有 MCP、有 Skill、有 SubAgent——这样才完整。"系统的"完整性"不取决于它使用了多少种组件，而取决于它是否解决了用户的问题。一个只用了单 Agent + System Prompt 的系统，如果它完美地解决了用户的问题，它就是"完整"的。

## 11.5 决策树：从任务特征到方案选择

前面四节分别讨论了不同层面的判断。加上第十章讨论的知识注入选型，我们有了一套完整的判断维度。现在把这些维度整合成一个决策流程。

![选型决策树：从任务特征到方案选择](images/11-selection-decision-tree.svg)

**第一步：任务是否需要工具交互？** 问自己：完成这个任务，模型是否需要"走出去"获取信息或执行操作？不需要（所有信息都在上下文中，模型可以直接回答）就用直接对话。需要（模型需要读文件、搜代码、查数据库、执行命令）就进入下一步。

**第二步：任务是否需要多步骤自主执行？** 问自己：这个工具交互是一次性的，还是需要根据结果决定下一步？一次性的（比如"查一下这个函数的定义"）用单次 Function Calling——模型调用一次工具，拿到结果，直接回答，不需要 Agent 的自主循环。多步骤的（比如"找到所有使用这个函数的地方，分析它们的调用模式"，模型需要先搜索、再读取、再分析、可能再搜索）就需要 Agent。

**第三步：任务是否需要不同的专业角色？** 问自己：这个任务的不同部分，是否需要不同的专业视角和评判标准？不需要（任务虽然复杂但角色单一）用单 Agent。需要（任务需要"写代码"和"审查代码"两种不同的视角）考虑多 Agent。但在选择多 Agent 之前，再问一个问题：单 Agent 的上下文是否撑得住？如果任务虽然需要不同视角但信息量不大，可以在单 Agent 中通过分阶段执行来模拟多角色——先用"设计者"的视角分析，再切换到"实现者"的视角编码。只有当上下文确实撑不住，或者角色切换导致明显的质量下降时，才真正使用多 Agent。

**第四步：能力扩展用什么方式？** 高频核心操作用内置工具，标准化外部集成用 MCP，持续行为约束用 Skill。大多数场景下三种方式会组合使用。

**第五步：知识注入用什么方式？** 根据第十章的判断框架：高频更新的事实性知识用 RAG，低频更新的行为模式用微调，少量的完整上下文用长上下文。同样，三种方式经常组合使用。

**决策树不是死板的流程图。** 实际的决策过程中，你可能会跳过某些步骤、回溯某些步骤、或者在多个步骤之间反复权衡。比如你可能在第三步决定用多 Agent，但在评估成本后发现 Token 预算不够，回到第三步重新考虑用单 Agent 的分阶段执行。决策树的价值不在于给你一个确定的答案，而在于帮你系统地考虑所有相关的维度——避免遗漏某个重要的判断因素。

**一个完整的例子。**

场景：你想让 AI 帮你为一个现有的 Go 微服务添加一个新的 API 端点。

第一步，需要工具交互吗？需要——Agent 需要读取现有的代码来理解项目结构、路由注册方式、数据模型。第二步，需要多步骤自主执行吗？需要——Agent 需要先读取路由文件了解注册方式，再读取已有的 Handler 了解代码风格，再读取数据模型了解数据结构，然后生成新的 Handler、路由注册、测试代码。第三步，需要不同的专业角色吗？不一定——"添加一个 API 端点"是一个角色单一的任务（代码编写者），如果你还需要 Agent 同时做代码审查可以考虑两个 Agent，但如果只是生成代码单 Agent 够用。第四步，能力扩展用什么？内置工具（读写文件、搜索代码）是核心，如果项目有特定的编码规范加载一个 Skill，如果需要查询数据库来了解数据模型加一个数据库 MCP。第五步，知识注入用什么？如果项目用的是公司内部框架需要注入框架文档——文档量不大（几千 Token）用长上下文（直接塞进 System Prompt 或者通过 Skill 加载），文档量大（几万 Token 以上）用 RAG。

最终方案：单 Agent + 内置工具 + 编码规范 Skill + 框架文档（长上下文或 RAG）。这个方案比"多 Agent + MCP + RAG"简单得多，但对于"添加一个 API 端点"这个任务来说，它已经足够了。

## 11.6 过度设计的陷阱

前面五节建立了一套选型框架。但框架本身不能防止一个最常见的错误：过度设计。

过度设计不是技术问题，是心理问题。它来自几种常见的心理倾向。

**"既然有，就该用"的心理。** 你花了两天时间搭建了一个 RAG 系统，现在你倾向于把所有的知识注入都通过 RAG 来做——即使有些知识只有几百 Token，直接写进 System Prompt 就行。你学会了多 Agent 的协作模式，现在你倾向于把所有复杂任务都拆成多 Agent——即使单 Agent 完全能搞定。这是沉没成本谬误的变体——你在某个方案上投入了时间和精力，所以你倾向于在更多的场景中使用它来"证明"这个投入是值得的。

**"更复杂 = 更专业"的心理。** 多 Agent 系统听起来比单 Agent 更"高级"，RAG + 微调 + 长上下文的组合听起来比单纯的长上下文更"全面"，MCP + Skill + 内置工具的全套配置听起来比只用内置工具更"完善"。但"高级"、"全面"、"完善"不等于"合适"。过度设计的根源是一种心理倾向：**用方案的"先进性"来评估方案的"适合性"。** MCP 比直接 API 调用"先进"，SubAgent 比单 Agent "先进"，所以它们一定更好——这个推理是错的。

**"万一以后需要"的心理。** "现在用直接对话就够了，但万一以后任务变复杂了呢？不如现在就搭建 Agent 系统，以后就不用改了。"这是过早优化的变体。你在为一个可能永远不会出现的需求付出现在的成本。而且当需求真的变化时，你现在搭建的系统可能并不适合——因为你不知道需求会怎么变。

**三个典型的过度设计案例。**

第一个案例：用 MCP + RAG 查询配置表。场景是一个内部工具需要根据用户的角色返回不同的权限配置，权限配置存储在一个表里总共 15 条记录。方案是开发一个 MCP Server 连接数据库，用 RAG 检索权限配置。问题在哪？15 条记录，总共可能不到 1000 Token。直接把这 15 条记录写进 System Prompt，AI 就能回答所有的权限查询——不需要 MCP，不需要 RAG，不需要数据库连接。这个方案引入了 MCP Server 的开发和维护成本、RAG 的索引和检索成本、数据库连接的管理成本——所有这些成本，解决的是一个"把 15 条记录放进 System Prompt"就能解决的问题。

第二个案例：用多 Agent 处理代码格式化。方案是一个 Agent 负责分析代码风格问题，一个负责修复缩进和格式，一个负责统一命名，一个负责添加注释，一个协调 Agent 负责汇总结果。五个 Agent，处理代码格式化。代码格式化是一个高度结构化的任务——规则是明确的、操作是确定的、不需要"创造性判断"。一个 Agent 加一个清晰的 System Prompt 就能搞定，甚至很多格式化任务根本不需要 AI——`gofmt`、`prettier`、`black` 这些传统工具做得更好、更快、更可靠。五个 Agent 的协调开销远远超过了任务本身的复杂度，而且多 Agent 的结果可能不一致：格式 Agent 把代码格式化了，命名 Agent 又改了格式 Agent 的输出，导致格式再次不一致。

第三个案例：用 Skill 定义一次性任务流程。你需要把一个 Python 2 的脚本迁移到 Python 3，这是一次性的任务——迁移完成后就不会再做了。方案是编写一个"Python 2 到 Python 3 迁移 Skill"，定义迁移的每个步骤、每个检查点、每个转换规则。这个 Skill 可能需要花你两个小时来编写和测试，然后你用它执行迁移花了一个小时，总共三个小时。如果你直接在提示词里写"请帮我把这个 Python 2 脚本迁移到 Python 3，注意以下几点……"，可能一个半小时就搞定了。Skill 的价值在于复用——同样的流程被执行多次时封装的投入才能被摊薄。一次性任务的封装投入无法被摊薄，它就是纯粹的额外成本。

**这三个案例的共同模式：没有先问"最简单的方案是否够用"。** 方案评估应该从最简单的方案开始——直接对话能不能解决？单 Agent + 内置工具能不能解决？需要标准化或复用吗？需要并行化或专业分工吗？每一步都是在上一步不够用的情况下才进入的。这就是 YAGNI 原则在 AI 系统设计中的应用——**不要因为"将来可能需要"就提前引入复杂度。**

有人会说："但如果一开始就设计好，后面就不用重构了。"这个论点在传统软件工程中有一定道理——重构的成本可能很高。但在 AI 系统中，这个论点的力度弱得多。AI 系统的核心逻辑在提示词和规范中，不在代码架构中。从"单 Agent + 内置工具"升级到"单 Agent + MCP"，主要的工作是把工具函数包装成 MCP Server——这不是"重构"，这是"包装"。从"单 Agent"升级到"多 Agent"，主要的工作是拆分 System Prompt 和定义协调逻辑——这也不是推倒重来。AI 系统的升级路径比传统软件更平滑，这意味着"先简单后复杂"的策略在 AI 系统中的风险更低。

**复杂度是有成本的。**

每增加一层复杂度，你就增加了一个可能出错的环节、一个需要维护的组件、一个需要理解的抽象、一个需要调试的层次。这些成本在系统正常运行时是隐性的——你感觉不到它们。但当系统出问题时，它们会集中爆发。一个只用直接对话的系统，出了问题就是"模型的回答不对"——检查 Prompt 就行。一个用了多 Agent + MCP + RAG + Skill 的系统，出了问题可能是：某个 Agent 的 System Prompt 有歧义、MCP Server 返回了格式错误的数据、RAG 检索到了不相关的文档、Skill 的规则和 Agent 的推理冲突、协调器的路由逻辑有 bug、Agent 之间的通信丢失了关键信息……排查空间呈指数级增长。

简单不是妥协。简单是一种选择——选择把复杂度留给真正需要它的地方。

---

选型框架到这里就建立起来了。但框架只是骨架——它告诉你"该用什么"，但没有告诉你"怎么用好"。

在所有的选型决策中，有一个能力是贯穿始终的：怎么和 AI 沟通。无论你选择直接对话还是 Agent，无论你用 MCP 还是 Skill，最终都要通过某种形式的"指令"来告诉 AI 你想要什么。这个"指令"的质量，直接决定了 AI 输出的质量。而更深层的问题是：有没有一种方式，能让 AI 在开始工作之前就"理解"整个项目的规范和约束——不是通过每次都写一大段 Prompt，而是通过一套结构化的规范定义？
